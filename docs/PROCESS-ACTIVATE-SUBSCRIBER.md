# תהליך: הפעלת מנוי אחרי שהשבוע נגמר

_08.09.2026. עד ש-Stripe מחובר (ראו `lib/trial.ts`), זה נעשה ביד. שלושה שלבים, בלי אדמין UI — לא בונים אחד בשביל אפס עד תוצאה אחת._

---

## 1. מגיע מייל

מ-`hello@getbetween.app`, עם נושא כמו "בקשה לרכישת זמן נוסף בממשק" — זה הנושא הקבוע שהפופ-אפ ממלא מראש כשמישהי נחסמת. הגוף מכיל את מה שהיא כתבה, וכתובת המייל שלה (`replyTo`, ולא בהכרח כתובת ההרשמה).

**קודם:** לוודא איתה בתשובה למייל שיש בפועל תשלום מוסכם — 5$ לחודש. זה לא מתבצע בקוד ואין קבלה אוטומטית.

## 2. מציאת המשתמשת ב-Supabase

מסך Authentication → Users בדשבורד, חיפוש לפי כתובת ההרשמה (לא בהכרח זהה לכתובת שממנה נשלח המייל — לבקש ממנה לוודא).

או ב-SQL:

```sql
select id, email from auth.users where email ilike '%החלק המזהה%';
```

## 3. הפעלה

```sql
update subscriptions set status = 'active' where user_id = 'המזהה-מהשלב-הקודם';
```

**זהו. אין תאריך תפוגה, אין שדה נוסף.** `status='active'` פותח גישה לצמיתות, בדיוק כמו חמש המשתמשות שגידרנו ב-05.09 (ראו `lib/trial.ts`, ההערה בראש הקובץ).

אם למשתמשת אין עדיין שורה בטבלה (לא סביר, כי היא כבר נחסמה — כלומר כבר יש לה שורת `trialing`), אפשר גם:

```sql
insert into subscriptions (user_id, status) values ('המזהה', 'active')
on conflict (user_id) do update set status = 'active';
```

## אימות

```sql
select status, trial_ends_at from subscriptions where user_id = 'המזהה';
```
מצפים ל-`status = 'active'`.

---

## מה לא לעשות

- **לא לגעת בשורות של משתמשות אחרות.** תמיד עם `where user_id = ...`, לעולם לא `update subscriptions set status='active'` בלי סינון.
- **לא לתת החזר/ביטול ידני דרך ה-SQL הזה.** מחיקת שורה או שינוי ל-`canceled` הוא פעולה נפרדת, ואין לה עדיין תהליך כתוב כי לא קרה אף פעם.

## מתי זה נגמר

ברגע שיש **משתמש אחד** מוכן לשלם, זה בדיוק האיתות לחבר את Stripe בפועל (`agents/_frozen/2026-08-29-all/dev-prompt.md`, התוכנית של אלכס, מותאמת ל-7 ימים ול-$5). אחרי זה ה-webhook כותב את השורה הזו לבד, והתהליך הידני הזה מתייתר.
